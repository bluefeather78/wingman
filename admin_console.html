A dry run calls the paid API at full cost and only skips the database writes, dumping what it would have written to a local JSON file. Committing that file applies those writes. It makes no API calls and costs nothing — the money was already spent by the run that produced it.

Scraper snapshots insert new rows inactive, exactly like a live scrape, and are deduplicated by URL against the whole table — committing the same file twice inserts nothing the second time. Nothing here ever activates a row; that is the Review queue tab.

Snapshot filenames carry a date only, so a second run on the same day overwrites the first one’s file. A snapshot is the last run of that date, not all of them.

Edit any value above to change it permanently — it saves immediately and becomes what every new run of that agent starts from. Changed values are highlighted, with a reset link back to the built-in default.

Min delay is the minimum gap between API calls. 5 s is the value that resolved this pipeline's repeated HTTP 429 rate limiting — lower it only for short sample runs. It also dominates wall time: a 1,300-row pass at 5 s takes roughly 110 minutes regardless of how fast the API responds. Timeout is the per-request read timeout; note a client-side timeout does not stop or refund work already running server-side, so setting it too low means paying for answers you never see. The two agents marked as sharing the search lock cannot run at the same time.
Everything sitting at is_active = false — rows the scraper found and opportunities students submitted themselves. Nothing in this repo activates a row automatically; both paths write inactive and stay that way until someone here says otherwise. Activating one puts it in front of students, so read the row before you tick it. Rejecting never deletes: the row stays in the table so its URL keeps blocking re-submission, it just drops out of this queue instead of coming back round every time.

A dry run calls the paid API at full cost and only skips the database writes, dumping what it would have written to a local JSON file. Committing that file applies those writes. It makes no API calls and costs nothing — the money was already spent by the run that produced it.

Scraper snapshots insert new rows inactive, exactly like a live scrape, and are deduplicated by URL against the whole table — committing the same file twice inserts nothing the second time. Nothing here ever activates a row; that is the Review queue tab.

Snapshot filenames carry a date only, so a second run on the same day overwrites the first one’s file. A snapshot is the last run of that date, not all of them.

Timing & rate limits

Editable — these are the defaults each run modal starts from
AgentAPIMin delayTimeoutShared search lockWrites
Edit any value above to change it permanently — it saves immediately and becomes what every new run of that agent starts from. Changed values are highlighted, with a reset link back to the built-in default.

Min delay is the minimum gap between API calls. 5 s is the value that resolved this pipeline's repeated HTTP 429 rate limiting — lower it only for short sample runs. It also dominates wall time: a 1,300-row pass at 5 s takes roughly 110 minutes regardless of how fast the API responds. Timeout is the per-request read timeout; note a client-side timeout does not stop or refund work already running server-side, so setting it too low means paying for answers you never see. The two agents marked as sharing the search lock cannot run at the same time.
Everything sitting at is_active = false — rows the scraper found and opportunities students submitted themselves. Nothing in this repo activates a row automatically; both paths write inactive and stay that way until someone here says otherwise. Activating one puts it in front of students, so read the row before you tick it. Rejecting never deletes: the row stays in the table so its URL keeps blocking re-submission, it just drops out of this queue instead of coming back round every time.

Signup recipes the Mailing List Finder proposed — how to join one program’s mailing list, in a form the server can replay for a student. Nothing here is executed until you mark it Verified: an unreviewed recipe is not a slightly-worse verified one, it is a form that may belong to the whole university rather than to this program. 73% of the catalog shares a domain with a different opportunity, so read Evidence — the quote that decided attribution — not the confidence score, which is the model grading its own work.

A verified recipe means we can submit a signup. Every provider here double opt-ins and we subscribe the student’s own address, so nobody — us included — can see whether they clicked the confirmation link. The app says “submitted”, never “subscribed”.

The trusted-domain allowlist — the one operator-controlled policy that governs every off-domain source in the app. It decides which third-party sites the deadline tracker may take a date from (its last-resort 4th search rung) and, once aggregator discovery ships, which guide sites a task may cite.

Trusted domains are shown to students and may back logistics, never eligibility. Blocked domains are dropped everywhere. A domain that is neither is pending: withheld from students by default, so an unknown site is safe. Verification (does the page really say this?) is separate and lives in code — this is only about how far to trust the source.

A trusted date is always marked estimated and names its source; the program’s own site is always preferred over anything here.

Add / update a domain

A full URL is fine — it is reduced to its bare domain. Blocking overrides an accidental parent-trust. Removing a row (below) returns the domain to pending.

The three lifecycle emails — a welcome at signup, a reminder before the free trial ends, and a cancellation confirmation. This is not a marketing system: there is no list, no segments, and deliberately no path anywhere in this repo that mails everybody at once.

Sending is Resend; the roster stays here. One address is handed over at the moment of sending and nothing syncs a contact list to a third party — that would mean continuously exporting the names and addresses of minors, and would need a privacy-policy edit and a TERMS_VERSION bump first.

The daily trial sweep is not run from this page. These routes are localhost-only and never mounted on Render, so a button here would only fire on days this machine is on — and the student whose trial ends tomorrow is exactly the one who will not be opening the app for us. The schedule lives in .github/workflows/lifecycle-emails.yml, which calls POST /api/email/sweep on the deployed service. The button below is a manual catch-up, and it is safe to press twice.
The email_sends table is missing. Run email_schema.sql in the Supabase SQL editor (it is idempotent), then restart with restart_server.ps1. Until then nothing is sent at all — a send claims its row before calling the provider, so no table means no claim, and no claim means no send. That is deliberate: sending with no record of having sent is how a daily sweep mails the same student every morning.

How the Wingman app works

The visual source-of-truth for the student-facing half of Wingman — the Expo app and its FastAPI backend. (Its sibling doc, the Catalog Control Room, covers the other half: the offline catalog pipeline and the ops console.)

01

Two halves, and how they're served

The frontend is an Expo (React Native + RN-web) app in frontend/ targeting web + iOS + Android from one codebase. The backend is a FastAPI service in app/ (the only Python thing deployed to Render). In dev they are two origins; in production they are one.

Frontend build
expo export -p web → frontend/dist (Render static site); native ships via EAS.
Two catalog caches
A vector-free catalog cache (OPPORTUNITIES_CACHE_TTL, 300s) served with a gzip + ETag; and the 768-dim match_vector embeddings behind CATALOG_VECTOR_CACHE_TTL (24h). Only /api/match reads vectors; the client route strips them.

Routes are files under frontend/app/ (expo-router — the path is the route). The branded tab names are load-bearing — never Home / Profile / Search / Tracker.

03

Auth — bearer + refresh, verified server-side

Identity is a signed JWT in an Authorization: Bearer header, never the request body — that is what closed the pre-migration IDOR on /api/data/*. Two token types, both HS256 over JWT_SECRET (which fails closed: unset → 503, never a guessable key).

Access token
45 min TTL, verified statelessly on every gated request (no DB hit). Carries ver for symmetry.
Refresh token
30 day TTL, presented only to /api/auth/refresh. Its ver is checked against users.token_version (bump = log out everywhere) and its single-use jti is rotated (refresh_jtis).
Passwords
Client sends SHA-256(password) as 64 hex chars; the server stores argon2 over that (64 MiB, 1–3s). Legacy bare-SHA rows upgrade transparently on next login.
Client token store
tokenStore.ts — expo-secure-store on native, localStorage on web (wingman.access_token / wingman.refresh_token), plus a cached wingman.session_user so startup skips a blocking refresh.
Server state (not client)
The Supabase users.data jsonb holds the whole app under three byte-stable keys: student-profile, hs-tracker-data (a JSON string), hs-tracker-saved. Reached via /api/data/{save,load}.

04

Subscription, trial & consent — and the two-tier shift

Every account starts a 7-day free trial converting to a $4.99/month Stripe plan. subscription_state(record) in app/core.py is the single source of truth both the client paywall and the server gate derive from, so they cannot disagree.

The important change from the prose docs: there is no longer an app-access lockout. Under the two-tier model (TWO_TIER_AI_PLAN.md), subscription_block_reason() always returns None — has_access is effectively always true for a signed-in account. A lapsed paid/comped account becomes Free rather than being walled off. The real gate is now a metered daily AI-action allowance at /api/ai, which answers 429, not 402 (see §05).

has_access rules
active → yes; trial → until trial_ends_at; beta/canceled → until subscription_end_at. NULL trial_ends_at = "clock not started", not expired (ensure_trial_started() stamps it on first sign-in).
Free tier allowance
FREE_TIER_DAILY_AI_ACTIONS (10), FIRST_DAY_AI_ACTIONS (20), same-class calls collapse inside a 300s window. Not yet enforced — ships in observe mode until FREE_TIER_AI_GATE_ENFORCED=1. Unlimited = paid; BUDGET_EXEMPT_USERIDS is the operator override.
Promo codes
Two kinds keyed by kind: a grant (BETAUSER → beta, +7d) redeemed against the row via /api/subscription/redeem-promo, no Stripe; a checkout discount (FREEMONTH, WELCOME10) passed to the Checkout Session. promo_codes_used enforces one-per-account.
Signup consent
Three checkboxes (18+; else parent/guardian per Terms §2; accept Terms + Privacy), re-checked server-side and stamped on the row (is_adult, parental_consent, terms_accepted_at, terms_version). TERMS_VERSION = 2026-09-07.
Stripe (sharp edge)
Not configured: STRIPE_API_KEY/STRIPE_PRICE_ID absent, so /api/subscription/checkout errors and Upgrade surfaces that. A /api/webhook/stripe endpoint exists for when it is. Everything upstream of payment (trial, promo grant/redeem, cancel bookkeeping) works without it.

Client side, (app)/_layout.tsx is still the paywall (redirect on an explicit has_access === false, hide tabs) and httpClient still flips the cached identity on any 402 — but because the server no longer emits an access-lockout 402, that machinery is effectively dormant today.

05

AI call flow — one door, feature-keyed

There is exactly one AI endpoint: POST /api/ai, taking {feature, inputs}. It replaced the old /api/messages and /api/messages-claude (S1-1). The server owns the prompt text, the provider, the tool config and the token budget; an unknown feature is a 400 that never reaches a model.

The prompts live in app/services/prompts.py — marquee M8, and every branch of the route is marquee M9 (a paid call). The provider is a property of the feature id: Gemini (gemini-3.5-flash-lite) for ranking / tag extraction / tracker extraction, and the deliberate Claude holdout (claude-haiku-4-5-20251001) for the profile chat + synthesis.

Client seam
httpClient.callFeature(feature, inputs) → POST /api/ai. Every src/lib/* module takes the call function as a parameter (dependency-injected, pure/testable). extractJSON() depth-scans the reply; callGeminiJSON (aiJson.ts) retries once on a parse failure.
Mock mode
No key → generate_mock_text pattern-matches the (server-built) system prompt, so the app is fully click-through-able offline. The AI route stays reachable signed-out precisely so mock mode works; the gate keys on whether a live key is configured, not the route.
Guardrails at the route
Rate limits (~30/min/user, ~120/min/IP), a concurrency lane (AI_MAX_CONCURRENCY=12, sheds with 503 + Retry-After), a 512 KB body cap (413), a 60s upstream timeout, and web search pinned off server-side.
Spend guards
A global daily circuit breaker (GLOBAL_DAILY_BUDGET_USD=25) that degrades to mock when tripped, and a per-user/per-row forced-deadline-recheck cooldown. Cost is attributed per call by feature id (exact, no substring guess).

06

The profile chat & its caching

My Vibe's chat drawer builds the student profile. Its two halves are cached asymmetrically, and the asymmetry is the point.

Openers — cached
The 3 starter questions depend only on the profile text, so they're safe to cache: a starterPool slot (10 generated, a rotating window of 3). Known RN gap: the pool is ported but not wired — the drawer currently calls the live 3-question path on each open.
Follow-ups — always live
profileChatNextQuestion is one live Claude call per bot turn and must stay so — a follow-up reacts to what the student just said, which a pool cannot. The transcript sent includes the bot lines, not just answers.
One merged extract
Tags + tag enrichment + basics tiles are ONE Gemini call, extractTagsAndBasics (profileTags.ts) — down from 3. A full profile update is 3 model calls (subjects, the merged extract, opener pool), ~5 counting enrichment top-ups.
Slot freshness
Exact profile-text identity (slot.profile === synthesized), no tolerance — swapping "robotics" for "chemistry" is a zero-word delta that must still invalidate. Every synthesis rebuilds all derived slots in the background.
Synthesis
Runs on drawer close (only if the student answered), rewriting the whole profile — the expensive call, on Claude, retried at a higher token ceiling if truncated (stop_reason).
MECE filter tags
Filter tags are mutually-exclusive, collectively-exhaustive themes at the altitude a program is described, not one tag per profile line. No cap on tag count; grouping (not truncation) controls the number.

07

Fresh Finds — matching

The finder narrows the catalog to what fits a student. Two layers: a client-side rank, and a server-side semantic recall.

Client rank
preFilter narrows by inferSubjects (a derived slot, deliberately kept off the merged extract because it's on the search critical path), then rankCandidates (ranking.ts) scores the pool via an AI call.
Server recall
POST /api/match (paid, require_subscription) embeds the student's selected themes + projects, recalls top-N by cosine over match_vector, drops verified-ineligible rows via an eligibility-gate model call, and returns the scored pool. {prewarm:true} embeds while the student is still on the theme picker.
Degrade path
No key, or circuit-breaker open → an honest recall-ordered, ungated list (no embeddings, no eligibility call) rather than a broken screen.

08

Quest Log — tracker & deadlines

Six buckets (summerPrograms, internships, researchCompetitions, pureCompetitions, conferences, journals). Deadlines are checked on demand and shared, not on a schedule.

Deadline check
GET /api/opportunities/{id}/deadline — a Claude web-search check (~$0.07) run the first time a student opens a row, cached 7 days and shared across all students. Bounded by a paid-check concurrency lane (PAID_CHECK_MAX_CONCURRENCY=4).
Write decision
deadline_write_decision() is the one place that decides whether a check may overwrite a row. Four outcomes, three of which write nothing and don't stamp: unverified-fallback (never searched), unparsed-fallback (searched, JSON unreadable), kept-existing (verified-empty over existing dates), and fresh, real search (write + stamp). not_running always writes.
Verified-source gate
The client may only DELETE dates on a verified source — isVerifiedDeadlineSource() (tracker.ts) accepts only cached and fresh, real search. Estimated dates are marked per-date and rendered "(estimated)".
Free batch mirror
GET /api/tracker/sync?ids= returns the catalog's cached deadline+task data for tracked ids in one call — no paid check, never throws.
Calendar sync
POST /api/calendar/sync writes to a dedicated "Highschool Wingman" calendar under the calendar.app.created scope (marquee M7 — it can never touch a student's own calendars). The calendar mirrors the Quest Log: the sweep deletes unmarked events too, so anything a student adds by hand is removed on the next sync. not_running rows are skipped.

09

Action items — the checklist that can't fabricate

Each row's application checklist is catalog data, generated by the 7th agent (generate_action_items.py) and verified line-by-line against the program's own page — the fix for a fabricated "Algebra 2 prerequisite" that no page stated.

The guarantee is in code
page_text.py: every distinctive word of a task must appear on the fetched page (claim_is_supported) and a page-backed task must supply a verbatim quote (quote_is_on_page). Failing the first drops the task; failing the second demotes it to generic. No fuzzy matching.
basis (page-backed vs generic)
Served from GET /api/opportunities/{id}/action-items. The client honours basis in exactly one place (normalizeVerifiedActionItems); anything a model produces in the browser is forced to generic. Home Base renders "From the program page" vs "Typical steps — confirm on the site".
Unfetchable page
Costs nothing — no model call — and gets a local per-type generic checklist. A fetch failure is a fact about our HTTP client, never about the program.

10

Lifecycle email

Three transactional emails via Resend — welcome at signup, trial_ending ~2 days before the trial expires, goodbye on cancel. Deliberately not a marketing system: no list, no broadcast, no path that mails everybody at once (the roster is largely minors).

Claim table
email_sends is written before Resend is called; its unique (userid, kind, dedupe_key) is what makes a repeated sweep safe. A mock send (no RESEND_API_KEY) writes no claim row. db/email_schema.sql gates the whole feature.
Triggers
welcome/goodbye are event-driven from app/routes/ (register, Google finish, cancel). trial_ending comes from POST /api/email/sweep (guarded by EMAIL_CRON_SECRET in a header, fails closed).
Sweep cron — DISARMED
.github/workflows/lifecycle-emails.yml carries workflow_dispatch only, so the trial reminder does not auto-send; someone must run it. Re-arming = uncommenting the cron + setting two secrets.
Opt-out
GET /api/email/unsubscribe answers HTML, carries an HMAC of the userid, and is honoured for all three kinds (even the defensibly-transactional two). Also: deadline-alert digest emails exist (DEADLINE_ALERT_RUNGS = 7,3,1).

11

Data rights — export & delete

Both self-serve endpoints ship (app/routes/account_data.py, DATA_DELETION_EXPORT_PLAN.md). Identity is always user.id from the verified token — there is no userid parameter anywhere, which is the "can't touch another user's data" guarantee.

Export
POST /api/account/export — assembles everything Wingman holds and returns it as one JSON file attachment. Rate-limited per hour.
Delete
POST /api/account/delete — immediate hard delete guarded by re-auth: either {passwordHash} re-verified server-side, or a single-use {reauthToken} from a Google re-auth flow (for Google-only accounts). A live Stripe subscription is cancelled first; if that fails, nothing is deleted.
Both ungated
Hang off get_current_user, not require_subscription — a lapsed account must still be able to take or erase its own data.

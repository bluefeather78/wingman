How the opportunity scraper works

Four ways a page reaches the pipeline (one — the walk-up — retired 2026-09-07), a router that stops third-party pages being thrown away, and — new this session — a per-candidate gate that reads each page once, says what kind of page it is, fills the row's fields, and hunts for a duplicate the URL match can't see. Everything still ends at one human gate before a student sees anything. Each box shows the rules inside it, whether running it costs money, and where it is still blind.

What runs on its own, and what waits for you. This is the line the diagram above is drawn around, and it is worth stating plainly because the two halves look continuous.

Automatic and free: a scrape captures leads as a side-effect — every page it consulted that did not become a row goes to the router, which classifies it and writes it onto a queue. Rejecting a row as a round-up in the console queues that page the moment you pick the reason.

Waiting for you, and only ever started by hand: every extractor — hub mining, name harvest, re-finding dead links — plus the search-angle scrape itself. No scheduler, no console button calls them. Most spend money, and the standing rule is that a paid run gets fresh approval each time.

So the queue fills itself and nothing ever drains it. That is deliberate: draining it spends, and everything it produces lands in a review queue that only a person can clear.

① Where pages come from live

Four ways a candidate page reaches the pipeline — the walk-up (last box) was retired 2026-09-07, folded into the classify pill's first-party-hub verdict. Of the three still live, two cost money to run; the rejected pile is free because a person already did the work.

Search anglesagents/scrape_opportunities.pyPAID

You give it a topic ("Marine Science programs"). The main discovery engine — and the only one that finds programs nobody has linked to.

inside the box
  1. Phase 1 — research. Prose out, web search on. Keeps the search's own record of which pages it really opened; that record is the only place a real URL exists.
  2. If it didn't search, ask again once. The model decides per call whether to search, and a silent call is free — so re-rolling is cheaper than arguing with it.
  3. Phase 2 — extract. Phase 1's notes plus the real URLs go in, strict JSON comes out, no search. Never merged into one call: asking for JSON up front collapses the search rate to near zero.
  4. Each candidate then passes through the discovery gate (below) before it can become a row. Pages that didn't become a program row go to the router instead of the bin.
Your rejected pilethe console's Reject buttonFREE

When you reject a row because it's a round-up, that page is fed straight back in — automatically, the moment you pick the reason. Better evidence than anything automated: you looked at the page and said what it is.

inside the box
  • The reason is the trigger, not the rejection. "Wrong page", "dead link", "not a fit" say nothing about a page being a round-up, so they route nothing. Only the round-up reason does.
  • It skips the title check. That check asks "is this about many programs?" — which you just answered, having actually read the page. All that's left is links them or names them.
  • It never drops what you flagged, runs in the background so a slow site can't hang the button, and remembers a "no" so a page judged not-a-round-up is never re-opened.
  • The one-off catch-up has been run over the whole pile: 349 rejected rows → 12 leads (8 link, 4 name); the other 323 are remembered as "not a round-up".
Walk up from the catalogwingman/walk_up_hubs.py — RETIRED 2026-09-07FREE

Retired 2026-09-07 as redundant. A university's own index links its programs on its own site, which the ≥6-off-site-domains router cannot see. This finder used to derive such an index by walking up from a trusted catalog row; that job is now done instead by the classify pill — when it tags a fetched page a first_party_hub it is queued as a same-domain lead for the miner, so a dedicated walk-up finder no longer earns its keep.

how it worked, while it existed
  1. Take a program you already activated — the strongest trust signal there is, since nothing here activates anything on its own.
  2. Go one level up its address. …/summer-programs/summer-institute → …/summer-programs/.
  3. Does that page link the program back? This was the proof. A page that doesn't is a shorter address, not an index — which is why a costs page covered in hundreds of links could never sneak through.
  4. Does it offer program pages beyond that one, and is it not a homepage? Densest first, ranked by how many of our own programs it really links.
the one live sweep it ran — free, no search at all
  • 1,325 activated programs → 612 distinct parent pages → 244 proven indexes — CMU's pre-college index alone had 12 of our rows under it and 25 more programs on it. Ten mined; the rest queued before the finder was retired.
Re-find a dead linkagents/refind_dead_links.pyPAID

A program whose stored link died is usually a program that moved, not one that ended. One narrow search per row.

inside the box
  • Only rows deactivated for a dead link, and only ones not already tried — each row is stamped, so a discontinued program is never re-paid for.
  • A replacement is accepted only if it is on the same site as the dead link, its page title names the program, and it hasn't dropped a word the old URL used to identify it. A blog or news post on that site is rejected outright.

② The router live — feeds the mining queue

The piece that stops good leads being thrown away. One question — does the page LINK its programs, or only NAME them? — answered by looking at the page, never by recognising its domain.

Links them, or only names them?wingman/discovered_leads.pyFREE
the whole rule
  1. Skip anything already a catalog row, already queued, or that can never be a source (social, shops, blog/news posts, YouTube, Reddit).
  2. Are there any links on the page at all? None means we never really received it — a site builder answered one round-up with 400KB and zero <a> tags. So no verdict: a confident wrong answer here just wastes the paid extractor on the same nothing.
  3. Does the title promise many opportunities? A plural — and the site's own name is stripped off the title first, because that suffix lies about the page.
  4. Links ≥ 6 different outside sites → hub mining. Distinct sites, not links.
  5. Otherwise, ≥ 2000 characters of prose for high schoolers → a names lead (recorded only). Neither → not a lead, and it says why.
why off-site links, and what it still can't see
  • Same-site links are mostly the site's own navigation, so counting them measures menu size. Distinct outside sites separate cleanly: round-ups scored 9–20, ordinary pages 1–3.
  • What this rule cannot see: a university index that links its programs on its own site — which the classify pill's first_party_hub verdict now catches instead, queuing it as a same-domain lead. (A dedicated walk-up finder used to derive it; retired 2026-09-07 as redundant with that verdict.)

③ The two extractors live — both have produced rows

Hub mining is far cheaper per candidate because a link needs no search; name harvest pays a search fee per program. Since 2026-09-07 both are the one agent — agents/mine_hub_pages.py drains both hub leads and name-only leads (--names), harvest_names.py being an imported helper. Both are commands you run — the router only ever queues.

Hub miningagents/mine_hub_pages.py · wingman/sitemap_hub.pymostly FREEPAID to classify + read

An institution's own index. The miner reads the site's own page list and lets a model pick the program pages — one cheap call in place of a dozen slug rules.

the primary path — sitemap + LLM
  1. Enumerate the union of the site's sitemap and the hub's own links; scope to URLs under the hub's own path (one 20,000-URL sitemap dropped to 18).
  2. Classify — the one paid step, ~$0.001/hub. Hand the scoped URL list to a model: paths in, program home pages out. No page fetch, no search. This replaces every slug drop-list.
  3. Drop a page that is the sub-page of another program page; a hub the classifier empties falls through to the old link-harvest miner, so recall is never worse.
what the runs measured
  • Sitemap+LLM selector: 22 real hubs, ~$0.0009/hub, ~100% precision, zero tuition/nav/staff junk.
  • The earlier link-harvest run: 43 hubs → 300 pages read → 144 rows, $0.29 — and the catalog's first local rows (Seattle Parks, the YMCA's BOLD & GOLD). Just over half of everything read is refused — the safety net working, not waste.
Name harvestagents/harvest_names.py (helper) · run via agents/mine_hub_pages.py --namesPAID

The page names programs but won't link them. The names are in the text; the URLs are not, so each has to be searched for. Merged into the hub miner 2026-09-07: harvest_names.py is now a helper library with no main() of its own — the miner drains a names lead down this path so a name-harvested row gets the same classify pill and embedding-dedupe hint as a hub-mined one. You aim it yourself (mine_hub_pages --hubs <url> --names, or a names lead via --from-leads) — free preview by default, and the name cap doubles as the spend ceiling.

three free checks before a single paid search
  1. Is the name really on the page? Every distinctive word of it, literally — a model can't list programs it merely remembers. Exact words, never fuzzy.
  2. Could it ever be proven? A name needs two words of its own, or no title could confirm it. Do we already have it? Strict catalog match. Same program named twice? Collapsed.
  3. Rank, then spend. Shorter names first; penalise a description and a name carrying the host's own brand. A quality floor decides — the count cap is just a ceiling.

④ The discovery gate — read once, classify, enrich, dedupe live (M9) — ran on 5 angles this session

New this session. Every candidate that survives the checks above passes through this gate before it becomes a row. It is one page fetch feeding three model steps, wired into the search-angle scrape and always on. This is where a page finally gets read rather than merely found.

Classify the pagewingman/classify_page.pyPAID — one no-search call

Reads the page's full text and returns one of four kinds — program, first-party hub (an institution listing its own programs), third-party hub (a blog naming others'), or none — plus a deterministic staleness check. The prompt is locked (a marquee decision); the call is a money seam.

the guarantees that live in code, not in the prompt
  • Staleness is a date regex, never the model. "The newest year on this page is ≥ 3 years old" is decided by counting years in the text — dates are exactly where models fabricate. A page with no date is kept, because it cannot be proven old.
  • Evidence must be on the page. A positive verdict owes a verbatim quote; if that quote isn't literally in the fetched text, the class is capped at low confidence and marked unverified.
  • Conservative v1: the model's judgement never drops a would-be row on its own. Only the date rule drops, and only in act mode. none is flagged and kept so its precision can be measured before it earns drop authority.
  • A page we cannot fetch costs nothing — no model call is made — and is kept as unreadable.
measured — full review queue, 279 rows, $0.4631
  • program 159 · first-party hub 38 · third-party hub 18 · none 20 · unreadable 44, and 11 dropped as stale by the date rule.
One read, then enrichwingman/combined_reader.pyPAID

The orchestrator that made this a gate rather than three separate agents re-fetching the same page. It fetches once, classifies, and — only for a fresh program — fills the row's fields and looks for a duplicate.

inside the box
  • Metadata comes from the page, not the model's memory. It reuses the refresh agent's own extraction (its approved prompt and field validation) on the text already in hand — so a gate-produced row is field-complete the moment it is saved, indistinguishable from one a refresh pass would produce.
  • This closes the "activate then it's still blank" gap for scraped rows: they arrive enriched, so activation needs no separate refresh run.
  • A hub, a none or an unreadable page skips enrichment — there is no single program to describe.
  • Wrapped whole: a gate failure inserts the row ungated rather than losing the candidate.
The duplicate the URL missedwingman/embed_common.py · dedupe_confidence.py · dedupe_embed_store.pymostly FREE

The name/URL dedupe catches the same program at the same address. This catches the same program at a different address — a Facebook page, an Empowerly listing, a moved URL — by comparing the meaning of the fields, not the string.

how it decides
  • Each row's fields (name + org + type + summary + eligibility) are embedded and matched against the catalog's own dedupe_vector index over every active row (stored in the database since 2026-09-02, not a local file). Fields beat page text — the high-similarity band is nearly pure duplicates, and it needs no fetch, so it covers rows whose page has since died.
  • A single score can't separate a duplicate from a sibling (two YoungArts categories look identical to an embedding), so confidence comes from independent signals agreeing — name identity, hard fields, same institution. The result is a tier: PROOF · CONFIDENT · ADJUDICATE · SIBLING · HINT.
  • Auto-merge stays off until each tier's false-positive rate is measured against your verdicts. For now the tier is a labelled hint on the row; a person still decides.
  • The index stays current on its own: activating a row now embeds it into the index (a paid ~$0.0002 call, best-effort), so the next scrape matches against everything you've made live. It holds 1,676 rows today.
measured — full review queue, 279 rows, $0.0036
  • 4 confident · 4 adjudicate · 10 hints — e.g. a re-discovered SHIP internship at cosine 0.968, and an intra-queue twin of Blue Marble Review found at two URLs. Three siblings were correctly not flagged.

⑤ Verify, review, and drain the queue live

The classic checks still run around the gate, and the one hard human gate is unchanged. New this session: the labels the gate writes make the queue triageable in one command.

Verify & dedupe (name / URL)wingman/url_validate · url_repair · url_dedupeFREE
inside the box
  • Store only a link the search actually retrieved; drop ad-mills; rescue an off-site mention to the program's own page; require the title to name the program.
  • If we already have the program at that URL, improve the existing row rather than adding a second. Flag, never silently discard — only an exact duplicate or a URL-less candidate is dropped.
Human reviewadmin consoleFREE

The one hard gate. Nothing reaches a student automatically: rows sit hidden until you activate, reject, merge or mark them duplicate. The queue now shows each row's class pill and any "possible duplicate of…" back-link, and a class filter, so a decision is a five-second spot-check instead of a cold read.

Bulk triage by verdictagents/triage_queue.pyFREE

Once the queue is classified, most of it sorts itself. This rejects the safe classes in one command instead of clicking through them — hubs (their programs are already mined), none pages, and stale programs.

inside the box
  • Never touches a fresh program (yours to activate) or an unreadable row (a fetch fail is about us, not the page). Rejecting is reversible — the row stays in the table, its URL still blocks re-submission.
  • Preview-first: no flags prints the class breakdown and writes nothing. Reuses the console's own moderation endpoint, so there is no logic drift.
  • On the current queue it would clear 87 of 279 — 56 hubs, 20 none, 11 stale — leaving 148 programs and 44 unreadable for you.
The learning loopseed ledger · agents/propose_angles.py · eval/grade_scraper_batch.pyFREE
inside the box
  • Each topic is scored on approvals against waste and switches itself off once mined out. Coverage gaps become proposed new topics, added switched-off.
  • Every verdict you record becomes a frozen test; any pipeline change is graded against them before it ships — zero approved rows lost is the bar. Grading the gate this way is the next agreed run.

What isn't built, and what's next

Open by decision, most-important first.

Grade the gate before a full-scale scrapeeval/grade_scraper_batch.pythe next run

The gate is wired always-on and has run once (5 angles). Before it drives a large scrape, it should be graded against the frozen verdicts — zero approved rows lost — exactly as every other pipeline change is. A paid run you trigger.

Auto-merge the safe duplicate tierswingman/dedupe_confidence.pymeasured, not yet enabled

CONFIDENT and PROOF tiers are eligible for reversible, audited auto-merge; today they are only labelled. Turning it on waits on the false-positive rate measured against your accumulating verdicts — 4 confident pairs came out of the last dedupe pass to start that count.

Local discovery (a metro)data/hubs_seattle.jsonpinned

Paused by decision. Two designs measured, neither worked: search-first (small orgs, no SEO) and hub-first (civic sites link branch locations, not programs).

Pages we cannot read at all— proposed —not built

~22% of candidate pages can't be opened — the site refuses us, it's a PDF, or the list is built in the browser. The gate keeps these as unreadable and flags them rather than guessing. A headless-render fallback is flagged, not solved, because it is the minority case.

The one rule that ties it together: a find is only trusted because the search truly retrieved its page and the page proves the program — never because a model asserted it. The gate is that rule made per-candidate: it reads the page, quotes it, and dates it by counting, so the label on every row is earned. And a find only reaches a student because you said yes. Everything else is about making that yes take five seconds.
